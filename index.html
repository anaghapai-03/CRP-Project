Part 1 — RSA Key Generation (with small numbers)

Real RSA-2048 uses 1024-bit primes (300+ digit numbers). We demonstrate the exact same math using small primes so you can verify every step by hand.

1
Choose two prime numbers p and q
Must be prime (only divisible by 1 and themselves). In real RSA-2048 these are ~1024 bits each.
Small demo: p = 61   q = 53
Real RSA: p ≈ 166546190895...1847 (309 digits)
2
Compute n = p × q (the modulus)
This is the public modulus. Everyone knows n. But nobody can find p and q back from n — that's the hard problem called integer factorisation.
n = 61 × 53 = 3233
Real RSA-2048: n is a 617-digit number
⚠ Breaking RSA = factoring n back into p×q. At 2048 bits this takes longer than the age of the universe with all computers on Earth.
3
Compute φ(n) = (p−1)(q−1) — Euler's Totient
φ(n) counts how many integers from 1 to n share no common factor with n. This number is kept completely secret.
φ(n) = (61−1) × (53−1)
φ(n) = 60 × 52 = 3120
4
Choose public exponent e = 65537
e must be coprime with φ(n) — meaning gcd(e, φ(n)) = 1. The number 65537 is standard because it is prime and makes encryption fast. In our small demo we use e = 17.
e = 17   (small demo)
gcd(17, 3120) = 1 ✓   (they share no common factor)
Real RSA: e = 65537 = 2¹⁶ + 1
Public Key = (n=3233, e=17)
5
Compute private exponent d = e⁻¹ mod φ(n)
d is the modular inverse of e — the number such that (d × e) mod φ(n) = 1. Computed using the Extended Euclidean Algorithm. This is your private key — never shared.
Find d such that: (d × 17) mod 3120 = 1
d = 2753
Verify: (2753 × 17) mod 3120 = 46801 mod 3120 = 1 ✓
Private Key = (n=3233, d=2753) — NEVER share d
6
Encrypt (sign) with private key: C = M^d mod n
Raise message M to the power of d, modulo n. Only the private key holder can do this. Let's sign message M = 65 (representing a hash byte).
C = 65^2753 mod 3233
C = 2790   ← this is the signature
7
Decrypt (verify) with public key: M = C^e mod n
Anyone with the public key raises the signature C to power e mod n. They get back the original message M. The math guarantees this works only because d and e are modular inverses.
M = 2790^17 mod 3233
M = 65 ✓   ← original message recovered
This works because: (M^d)^e ≡ M^(d×e) ≡ M^1 ≡ M (mod n) — by Euler's theorem

Part 2 — SHA-256 Hashing (avalanche effect demo)

SHA-256 internally runs 64 rounds of bitwise operations (AND, OR, XOR, rotate) on 512-bit message blocks. The output is always exactly 256 bits (64 hex characters). It is a one-way function — you cannot reverse it.

1
Pre-processing — pad the message to 512-bit blocks
The message bytes are padded: append a 1 bit, then zeros, then the 64-bit length. This ensures the input always fits exactly into 512-bit blocks.
"Hi" = 0x48 0x69 → pad → 48 69 80 00 00...00 00 00 00 10
The 0x80 = appended 1-bit. Final 8 bytes = message length in bits (16 bits = 0x10)
2
Initialise 8 hash values h₀…h₇
These are fixed constants derived from the fractional parts of square roots of the first 8 primes (2,3,5,7,11,13,17,19).
h₀ = 6a09e667   h₁ = bb67ae85
h₂ = 3c6ef372   h₃ = a54ff53a
h₄ = 510e527f   h₅ = 9b05688c
h₆ = 1f83d9ab   h₇ = 5be0cd19
3
64 rounds of compression per block
Each round uses bitwise operations on the 8 working variables a,b,c,d,e,f,g,h plus a round constant K and a message schedule word W.
Σ₁(e) = ROTR²⁵(e) XOR ROTR¹¹(e) XOR ROTR⁶(e)
Ch(e,f,g) = (e AND f) XOR (NOT e AND g)
T₁ = h + Σ₁(e) + Ch(e,f,g) + K[i] + W[i]
T₂ = Σ₀(a) + Maj(a,b,c)
After 64 rounds: add compressed values back to h₀…h₇, repeat for next block
4
Final hash = concatenate h₀…h₇
The 8 final 32-bit values concatenated give the 256-bit (64 hex character) hash. The avalanche effect: changing one input bit flips ~128 output bits on average.
"Hello" → 185f8db3...7fd2dbc0 (64 chars)
"hello" → 2cf24dba...0e1f0d68 (64 chars)
One capital letter changed → completely different 256-bit output (avalanche effect)

Part 3 — AES-256-GCM Encryption (step by step)

AES operates on a 4×4 grid of bytes called a state. It runs 14 rounds of 4 transformations for AES-256. GCM mode adds authentication on top.

1
Key Expansion — one 256-bit key becomes 15 round keys
The 32-byte (256-bit) AES key is expanded into 15 separate 128-bit round keys using a Key Schedule. Each round uses a different key.
Original key (256 bits): 2b7e151628aed2a6abf71588...
Round key 0: 2b7e1516 28aed2a6 abf71588 09cf4f3c
Round key 1: a0fafe17 88542cb1 23a33939 2a6c7605
…14 round keys total for AES-256
2
AddRoundKey — XOR the state with the round key
The 16-byte plaintext block is arranged into a 4×4 state matrix. XOR each byte with the corresponding byte of the round key. XOR is reversible — that's what makes decryption possible.
Plaintext byte: 0x32   Key byte: 0x2b
0x32 XOR 0x2b = 0x19
0011 0010 XOR 0010 1011 = 0001 1001 = 0x19
3
SubBytes — substitute each byte using S-Box
Every byte in the state is replaced using a fixed 256-entry lookup table called the S-Box (Substitution Box). This provides non-linearity — without it, AES would be breakable by linear algebra.
Input byte: 0x53
S-Box[0x53] = 0xed
Input byte: 0x00 → S-Box[0x00] = 0x63
S-Box is constructed using multiplicative inverse in GF(2⁸) — Galois Field arithmetic
4
ShiftRows — rotate each row of the state matrix
The 4×4 state is treated as 4 rows. Row 0 stays. Row 1 shifts left by 1. Row 2 shifts left by 2. Row 3 shifts left by 3. This mixes bytes across columns.
Before: [a0 a1 a2 a3] [b0 b1 b2 b3] [c0 c1 c2 c3] [d0 d1 d2 d3]
After: [a0 a1 a2 a3] [b1 b2 b3 b0] [c2 c3 c0 c1] [d3 d0 d1 d2]
5
MixColumns — multiply each column by a matrix in GF(2⁸)
Each 4-byte column is multiplied by a fixed matrix using Galois Field arithmetic. This provides diffusion — each output byte depends on all 4 input bytes of the column.
Column [a, b, c, d] becomes:
new_a = 2a XOR 3b XOR c XOR d
new_b = a XOR 2b XOR 3c XOR d
new_c = a XOR b XOR 2c XOR 3d
new_d = 3a XOR b XOR c XOR 2d
"Multiply by 2" in GF(2⁸) = left shift + conditional XOR with 0x1b if overflow
6
Repeat 14 rounds, then GCM authentication tag
Steps 2–5 repeat 14 times (AES-256). GCM mode then uses GHASH — a polynomial multiplication over GF(2¹²⁸) — to compute a 128-bit authentication tag over the ciphertext. This tag detects any tampering.
GHASH(H, A, C) = 128-bit auth tag
H = AES_K(0¹²⁸)   (encrypt a block of zeros with the key)
If even 1 bit of ciphertext is flipped → completely different tag → decryption throws error

Part 4 — PBKDF2 Key Derivation (password → key)

A human password like "hello123" is weak — only ~40 bits of entropy. PBKDF2 stretches it into a strong 256-bit AES key by running SHA-256 100,000 times.

1
PBKDF2(password, salt, iterations, keylen)
Password and salt are fed into HMAC-SHA256. The output is fed back as input. This is repeated 100,000 times. The final output is the AES key.
U₁ = HMAC-SHA256(password, salt || 0x00000001)
U₂ = HMAC-SHA256(password, U₁)
U₃ = HMAC-SHA256(password, U₂)
… repeat 100,000 times …
Key = U₁ XOR U₂ XOR U₃ XOR … XOR U₁₀₀₀₀₀
2
Why 100,000 iterations?
An attacker trying to brute-force your password must run PBKDF2 for every guess. 100,000 iterations means each guess takes ~0.1 seconds on modern hardware.
Passwords to try: 100,000,000 (common passwords list)
Without PBKDF2: ~0.001s per guess → cracked in 27 hours
With PBKDF2 × 100k: ~0.1s per guess → cracked in 270,000 hours
The salt prevents precomputed rainbow table attacks — same password, different salt = completely different key
